# R22 Hydration 边界：什么会被采纳，什么不会

对应 TASK 02、TASK 03。测量于 `bb8334fc`。

---

## 1. 结论先行

**控制流分支内的子组件不被采纳，这是设计行为，不是缺陷。**

但此前没有任何用户可见的文档说明这件事。消费者会看到「hydration 后 DOM 看起来正确」，
却不知道那部分子树是重建的。

---

## 2. 实测

三种位置，同一组件 `Kid`：

| 位置                                     | hydration 后 `Kid` 的节点身份 |
| ---------------------------------------- | ----------------------------- |
| 顶层（`<Kid/>` 直接作为 `App` 的子节点） | **保持**                      |
| `<Show>` 分支内                          | **重建**                      |
| `<For>` 项内                             | **重建**                      |

`onHydrationError` 在前两种失败情况下**都没有被调用**——没有诊断，静默回退。

---

## 3. 机制

`autoHydrateComponent` 的第一道守卫：

```ts
const session = currentSession()
if (!session || !session.active || createFrameDepth > 0) {
  return create() // 客户端渲染，无诊断
}
```

编译器在控制流区域内生成：

```js
$zeusHydration.mount(() => {
  $zeusMountShow(..., () => $zeusCreateComponent(Kid, { v: "x" }), ...)
})
```

`mount()` 的定义就是：

```ts
/** Runs dynamic-region mounting with component adoption disabled. */
mount(run: () => void): void {
  withHydrationCreateFrame(run)     // createFrameDepth += 1
}
```

所以分支内的任何 `autoHydrateComponent` 都会看到 `createFrameDepth > 0`，走 `create()`。

**这是显式的设计选择**：动态区域的子组件无法可靠匹配服务端与客户端的结构
（取决于运行时的条件与列表内容），强行采纳比重建风险更大。

---

## 4. 为什么这不构成 TASK 03 的「静默重建」

TASK 03 要求：

> 不允许未知情况下静默重建整棵 DOM。

这里的情况是**已知且局部**的：

- 重建范围限定在控制流分支内；
- 分支外的节点全部保持身份；
- 这是编译器的决定，不是运行时的猜测。

但**「已知」目前只存在于源码注释里**。消费者的可见文档没有这一条，
所以从用户角度看它仍是静默的。

### §6 是否应该诊断

两种立场：

**应该诊断。** 消费者写 `<Show><HeavyComponent/></Show>` 并期待 hydration 复用，
却得到重建——这在性能敏感场景是实质差异。

**不应该诊断。** 每次 Show 分支渲染都报告一次，会让正常的 hydration 充满噪音；
而且「分支内重建」是正确行为，不是错误。

**本轮不做决定。** 这需要产品判断：hydration 的性能承诺是否覆盖控制流分支。
记录下来，不擅自加诊断。
