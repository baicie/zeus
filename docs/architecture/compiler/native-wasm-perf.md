# Native 与 WASM 编译器的实测差异（R22 TASK 55）

测量时间：2026-11-22
命令：`pnpm bench:compiler-hosts --iterations 200`
数据：`temp/bench/compiler-hosts.json`
环境：darwin-arm64，Node 22.12.0（**非专用基准机**）

---

## 1. 结论

| 指标               | native       | wasm         | 比值           |
| ------------------ | ------------ | ------------ | -------------- |
| 加载（可首次转换） | 11–18 ms     | 20–31 ms     | ≈ 1.7×         |
| 首次转换（cold）   | 3.6 ms       | 14.6 ms      | ≈ 4×           |
| 热转换（中位数）   | 0.11–0.33 ms | 0.13–0.17 ms | **1.09–1.26×** |
| 输出字节           | 2291         | 2291         | 完全一致       |

**代码字节级完全一致**——这是本任务唯一断言的部分。两套宿主共用同一个 Rust
编译器的价值就在这里，而这个断言是逐字节比较，不是比长度。

热路径上 WASM 比 native 慢 **9%–26%**。差距比预期小，因为单次转换只有
0.1–0.3 ms，时间主要花在跨边界（JSON 序列化 + 线性内存拷贝）而不是编译本身。

**加载与首次转换的差距（1.7× / 4×）才是浏览器场景的真实成本**，而热路径
差距在编辑器这类高频调用场景才有意义。

---

## 2. 这个结论是在什么条件下得到的

### 2.1 迭代数低于 200 时结论不可靠

同一个二进制、同一台机器，连续三次 `--iterations 300`（实际跑 50 次时）：

| 运行 | native | wasm  | ratio     |
| ---- | ------ | ----- | --------- |
| 1    | 0.110  | 0.128 | **1.164** |
| 2    | 0.245  | 0.150 | **0.612** |
| 3    | 0.334  | 0.152 | **0.455** |

**同一份代码，三次运行 ratio 从 0.455 到 1.164**，相差 2.5 倍。那不是宿主的
差异，那是机器上别的东西。

`--iterations 200` 之后：

| 运行 | native 离散度 | wasm 离散度 | ratio | 判定     |
| ---- | ------------- | ----------- | ----- | -------- |
| 1    | 8%            | 15%         | 1.261 | MEASURED |
| 2    | 6%            | 15%         | 1.152 | MEASURED |
| 3    | 2%            | 2%          | 1.183 | MEASURED |
| 4    | 5%            | 4%          | 1.092 | MEASURED |

### 2.2 脚本会自己判定 INCONCLUSIVE

按 R21 TASK D 的要求（「机器噪声过大时，明确标记 INCONCLUSIVE」），benchmark
计算每个宿主的 **相对中位绝对偏差**（MAD / median），超过 `--max-dispersion`
（默认 20%）时：

- 打印 `INCONCLUSIVE`；
- **省略 ratio**，而不是发布一个数据支撑不了的数字；
- 退出码仍为 0——机器不稳定不是编译器的缺陷，把它变成红灯会让人学会忽略
  这个检查。

选 MAD 而不是极差：一次被调度打断的采样能让极差动几百个百分点，而几乎不动
中位数。

## 3. 这个断言发现了什么

第一版 benchmark 比较的是 `generatedBytes`，通过了。改成直接比较 `code`
字符串后，发现 **SourceMap 的 JSON 键顺序在两个宿主间不同**：

```
native: version,sources,sourcesContent,names,mappings,file
wasm  : version,file,sources,sourcesContent,names,mappings
```

所有字段的值完全相同，只有序列化顺序不同。这不是语义差异，但**长度相等的
比较会把它和真正的差异一起放过**。现在比较的是 `code` 的逐字节相等，并且
失败时会指出第一个不同的字节位置与两侧上下文。

SourceMap 的键序差异没有修——它是 JSON 对象，键序不承载语义，改它只会让
两侧为了对齐而增加无意义的耦合。
