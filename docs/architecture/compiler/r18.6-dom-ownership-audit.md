### 矩阵读出的三点

1. **`SourceIndex` 只有 2 个使用者**（`emit_module`、`emit_components`），
   都在编排层。DOM 叶子函数一个都不用。这意味着 DOM 原语不与源文件
   位置耦合，迁移风险低。

2. **`ForAccessorScope` 只有 `emit_for_mount_call` 用**。它不是共享状态，
   是 For 发射的局部上下文。迁移时跟着走即可，不需要提升到 infra。

3. **`NameAllocator` 有 12 个使用者**，`CodeWriter` 有 18 个（全部）。
   这两个是真正的跨目标共享能力，必须留在 `infra`。

## 3. 三个关键类型的归属

TASK G 指出"`GeneratedComponent`、`DynamicBinding`、`RuntimeNames` 的归属
可能比 `ComponentEmitter` 的字段拆分更重要"。逐个判断：

### `GeneratedComponent` — 归 DOM

```
id, start, end, root: RootIr, root_id,
template_name, element_name, template_html, is_svg,
root_component, root_builtin, bindings: Vec<DynamicBinding>
```

它持有**DOM 模板**（`template_html`）、模板变量名（`template_name`）、
元素名（`element_name`）。SSR 发射器**不使用它**——`ssr.rs` 从 `ModuleIr`
直接发射，不经过组件对象。

**结论：DOM 专属。** 应移到 `dom/model.rs`。

### `DynamicBinding` — 归 DOM

它描述"要挂到某个节点上的绑定"，枚举成员是
`Text` / `Node` / `TextContent` / `Attribute` / `Event` / `Ref` / `DynamicRegion`。
SSR 有自己的一套属性发射，不读这个枚举。

**结论：DOM 专属。** 应移到 `dom/model.rs`。

### `RuntimeNames` — 跨目标共享，留在 `mod.rs` 或 `infra`

它把 `RuntimeHelper` 的每个成员映射到一个**分配后的标识符**
（`$zeusBindText` 等），供 DOM 与 SSR 共用同一套运行时导入名。

**结论：不是 DOM 专属。** 它依赖 `RuntimeHelper`（在 `analysis.rs`）
与 `NameAllocator`（在 `infra.rs`）。留在编排层，不搬。

### `ComponentEmitter` — 只是参数包

```rust
struct ComponentEmitter<'a> {
    runtime: &'a RuntimeNames,
    locator_attribute: &'a str,
    names: &'a mut NameAllocator,
    auto_hydrate: bool,
}
```

四个字段，三个是不可变引用。**它没有状态设计问题**——TASK F 明确要求
不要根据字段数量假设缺陷，测量结果支持这一点：真正的耦合不在这个结构体，
而在 §4 描述的调用关系。

## 4. 真正的耦合点

hydration 拆分失败过一次，原因当时被误判。现在有事实：

`emit_auto_hydration_binding`（854–1089，235 行）调用 **12 个** `mod.rs` 函数：

```
emit_attribute_binding   emit_property_binding   emit_ref_binding
emit_spread_binding      emit_text_content_binding
emit_component_call      emit_dynamic_region_value
emit_event_binding       emit_for_mount_call
emit_show_mount_call     emit_transition_mount_call
emit_component_create_body  ← the aggregate
```

前 11 个是叶子（≤2 次内部调用）。第 12 个是聚合器，只在
`emit_auto_hydrated_component` 的 **fallback 路径**用一次。

**结论**：如果 11 个叶子属于 `dom/bindings.rs`，hydration 属于
`dom/hydration.rs`，那么 `hydration → bindings` 是同层依赖，合法；
`hydration → component`（`emit_component_create_body`）是 hydration 依赖
编排器，**必须禁止**。

fallback 通过**闭包参数**传入，不是十几个回调——这是 TASK I 允许的
单一注入点，语义是"无法 hydrate 时交给普通发射器"。

## 5. TARGET G 的模块结构

候选设计对了一半。按 §3 的类型归属修正：

```
codegen/
  mod.rs          顶层编排：emit_module, RuntimeNames, ComponentEmitter(参数包)
  infra.rs        CodeWriter, NameAllocator, quote_js（跨目标）
  analysis.rs     （已有）
  emit_plan.rs    （已有）
  ssr.rs          （已有）
  dom/
    mod.rs        DOM 子系统的重导出 + GeneratedComponent 构造
    model.rs      GeneratedComponent, DynamicBinding, RootBuiltin
    component.rs  emit_components, emit_component, emit_component_create_body
    bindings.rs   12 个叶子绑定/挂载发射器
    hydration.rs  emit_auto_hydrated_component 及其子树
```

### 与候选设计的差异

| 候选                    | 实际                             | 理由                                                       |
| ----------------------- | -------------------------------- | ---------------------------------------------------------- |
| `dom/mod.rs` 只做重导出 | 需要 + `GeneratedComponent` 构造 | 构造函数依赖 `RootIr` 与 `DynamicBinding`，是 DOM 内部操作 |
| `RuntimeNames` 未提     | 留在 `codegen/mod.rs`            | 跨目标共享，不是 DOM 专属                                  |
| `ComponentEmitter` 未提 | 留在 `codegen/mod.rs`            | 它是编排器传给 DOM 的参数包                                |

### 依赖方向（预期）

```
codegen/mod.rs
  → dom/mod.rs, dom/component.rs, dom/hydration.rs, ssr.rs, infra.rs
dom/component.rs
  → dom/model.rs, dom/bindings.rs, infra.rs
dom/hydration.rs
  → dom/bindings.rs, dom/model.rs, infra.rs
dom/bindings.rs
  → dom/model.rs, infra.rs
dom/model.rs
  → infra.rs, ir.rs
ssr.rs
  → infra.rs, ir.rs, support/*
```

**禁止**：`dom/hydration.rs → dom/component.rs`（这是 TASK J 的对抗测试目标）。
