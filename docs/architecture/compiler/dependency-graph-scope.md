# 依赖图检查器的适用范围

`crates/zeus_compiler/tests/depgraph.rs` 是 `crates/zeus_compiler/tests/boundaries.rs`
背后的事实来源。边界测试断言"这个 crate 没有循环依赖"这类结论，
但结论的可信度完全取决于检查器**实际能看到什么**。

本文记录它能看到什么、看不到什么，以及为什么。

---

## 1. 它读取什么

| 来源                       | 处理                                                      |
| -------------------------- | --------------------------------------------------------- |
| `use` 语句                 | 展开 `use` 树（含分组与重命名），按 Rust 的作用域规则解析 |
| 表达式路径（`Expr::Path`） | 经 `syn::visit::Visit` 遍历，覆盖全部表达式位置           |
| 外部 crate                 | 从本 crate 的 `Cargo.toml` 读取 `[dependencies]` 等的键名 |

**不读取**：类型路径（`Type::Path`）、宏体、字符串、注释。

---

## 2. 名称解析的七类

| #   | 类别                                           | 判定方式                              | 是否产生边                   |
| --- | ---------------------------------------------- | ------------------------------------- | ---------------------------- |
| 1   | crate 模块路径（`a::b`）                       | 查已知模块集合，取最深命中            | 是                           |
| 2   | 当前模块子模块（`b::work` 在 `a` 中 → `a::b`） | 先按当前模块拼接，再回退 crate 根     | 是                           |
| 3   | 兄弟模块                                       | 同上，由回退得到                      | 是                           |
| 4   | 外部 crate（`serde::X`）                       | 查 `Cargo.toml` 的依赖键              | 否（`Resolution::External`） |
| 5   | 类型关联项（`usize::MAX`、`u32::try_from`）    | 根部不是已知模块                      | 否                           |
| 6   | `use` alias（`use b::f as g; g()`）            | 边由 `use` 语句产生；调用点不额外产生 | 是（经 import）              |
| 7   | 局部作用域符号（`let b = 1`）                  | 单段路径，不进入解析                  | 否                           |

### 为什么类别 5 不能靠"首字母小写"判断

早期实现用 `root` 是否小写开头区分模块与类型。`usize::MAX` 因此被当作
模块 `usize`，报"no such module"。现在改为**查真实模块集合**：
`usize` 不是模块，所以不是边。这条规则同时覆盖了 `u32::try_from`、
`str::from_utf8` 以及未来任何原始类型上的关联项。

### 为什么类别 6 不解析调用点

`use crate::b::work as do_it;` 之后 `do_it()` 是本地绑定。
判断它指向 `b::work` 需要符号表；检查器没有符号表，也不会假装有。
边由 `use` 语句给出，语义上等价——**只要有导入，就一定有依赖**。

---

## 3. 已知盲区

### 3.1 宏体

```rust
pub fn f() { println!("{}", b::num()); }
```

`syn` 把宏体解析为未结构化的 `TokenStream`。要从中找出限定路径，
必须为任意宏语法重新实现表达式解析；而对 `ident :: ident` 做朴素的
token 匹配，会把 `format!("a::b")` 字符串字面量里的内容当成边。

**结论：检查器看不穿宏展开。** 只存在于宏体内部的依赖对它不可见。

对当前 crate 而言这是可接受的——模块调用不写在宏里。但这是**分析的局限**，
不是代码的性质。`a_qualified_path_inside_a_macro_body_is_not_seen` 专门
钉住这个行为：如果它开始通过，说明局限变了，`qualified_paths` 的文档注释
就过期了。

### 3.2 类型路径

```rust
pub fn f(_x: crate::b::Thing) -> Option<crate::b::Thing> { None }
```

`crate::b::Thing` 是类型，不是运行期依赖。把它算作边会让每个文件因为
签名里提到类型就产生依赖，真正的边会被淹没。

**结论：类型路径不产生边。** 如果一个模块**只**在类型位置被提到，
检查器认为它不依赖那个模块——这在"运行时耦合"的意义上是正确的，
在"编译期耦合"的意义上不是。

### 3.3 裸根路径只保留第一段

```rust
use dom::emit::emit_component;   // in codegen/mod.rs
```

记录成 `codegen -> codegen::dom`，**不是** `codegen -> codegen::dom::emit`。

后果：一个环如果经由子模块再回到父模块，且父模块只通过中间模块相连，
可能被漏掉。R18.6 就遇到了这个情形——`dom/emit.rs` 依赖 `codegen`
（为了 `RuntimeNames`），`codegen` 依赖 `dom::emit`（为了 `emit_component`），
但检查器看到的是 `codegen -> codegen::dom`，所以没报环。

尝试过保留完整路径，**已回退**：那会改变 `resolve_use` 对所有调用方的含义，
包括兄弟模块解析的既有测试，需要的是模块集合感知的 API，不是这一分支的补丁。

**实际影响**：真实的环是 `codegen <-> RuntimeNames`，而 `RuntimeNames`
住在 `codegen` 里。这个环是已知的、有意的（见 §6 的尝试记录），
不是检查器漏掉的隐患。

### 3.4 由 trait 解析决定的调用

```rust
x.method()   // 方法定义在哪个模块，取决于 impl 解析
```

方法调用不是限定路径，检查器不解析它。这同样需要完整的类型信息。

---

## 4. 检查器能回答与不能回答的问题

| 问题                                       | 能否回答             |
| ------------------------------------------ | -------------------- |
| 这两个模块之间有 `use` 依赖吗              | 是                   |
| 有通过限定路径的直接调用依赖吗             | 是                   |
| 存在循环依赖吗（在能被看到的边构成的图上） | 是                   |
| 某个类型在两个模块之间共享吗               | 否（类型路径不算边） |
| 宏展开后有依赖吗                           | 否                   |
| trait 方法实现在哪个模块                   | 否                   |

**"无循环"这个结论的准确含义是**：在限定路径调用 + `use` 导入构成的
依赖图上，不存在环。它**不**意味着两个模块在语义上完全解耦。

---

## 5. 维护规则

1. **不要用手写清单代替推导。** 外部 crate 名单曾经是硬编码数组，
   现在读 `Cargo.toml`；根模块名曾经是硬编码名单，现在查模块集合。
   两份清单都造成过漏报。
2. **不要用首字母大小写区分模块与类型。** 用真实模块集合。
3. **新增盲区必须在这里登记，并配一条钉住该行为的测试。**
   一个未被记录的盲区，会让"检查通过"变成一句空话。
4. **修复后必须验证反事实。** 新测试在修复前要真的失败；否则它
   只证明了"现在的代码能跑"，不能证明"检查器能发现这个问题"。
