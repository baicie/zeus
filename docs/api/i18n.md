# i18n

`@zeus-js/i18n` is an opt-in runtime for typed, reactive, ICU-based
internationalization. It is a separate entry point on purpose: an application
that never localizes must not download message formatting, and `@zeus-js/zeus`
must not depend on it.

First languages are `en` and `zh-CN`. Adding another means adding a catalog and
one entry in `SUPPORTED_LOCALES` — never widening the type to `string`, which
would let a typo become a silent fallback.

## Creating an instance

```ts
import { createI18n } from '@zeus-js/i18n'
import { en } from './locales/en'
import { zhCN } from './locales/zh-CN'

const i18n = createI18n({
  messages: { en, 'zh-CN': zhCN },
  initialLocale: negotiateLocale(navigator.languages) ?? 'en',
})
```

`messages.en` is required and is the fallback: every key resolves to at least
this catalog, so the first paint never shows a raw key. Other locales may be
supplied up front or loaded on demand.

Every instance is isolated. Two instances in one page can render different
languages (a settings preview, a documentation sample), and a server can hold
one per request. There is no global locale.

## Rendering

```tsx
function SaveButton() {
  // Reading `t` subscribes to the locale signal; a switch re-renders this text
  // node and nothing else.
  return <button>{i18n.t('common.save')}</button>
}
```

```ts
i18n.formatNumber(1234567.89) // 1,234,567.89 / 1,234,567.89
i18n.formatDate(date, { dateStyle: 'medium' })
i18n.formatRelative(-2, 'day') // "2 days ago" / "2 天前"
```

Dates and numbers go through `Intl`, never through string assembly. An invalid
date formats to `''` rather than `Invalid Date`.

## Messages held as data

State that outlives a render — a toast, a failed request, a status line — must
keep the key, not the rendered string:

```ts
const toast = i18n.message('admin.users.saved', { count: 3 })
// later, possibly after the user switched languages:
element.textContent = i18n.resolve(toast)
```

Rendering eagerly would freeze the message in the language it was produced in,
which is how mixed-language UIs happen. `i18n.raw(text)` wraps content that is
not translatable by definition — a server message with no code, a file path, a
compiler diagnostic — and returns it unchanged.

## Switching

```ts
await i18n.setLocale('zh-CN')
```

The promise resolves once the new catalog is active, and rejects if it could not
be loaded — in which case the previous locale stays in place, because showing the
previous language is correct text and showing keys is not.

Switching never reloads the page, recreates a router, or clears state. It only
updates the locale signal, so whatever the app holds (a draft, a stream cursor, a
form) is untouched.

Rapid switches settle on the **last request**, not the last response. If the
Chinese catalog is slow and the user picks English in the meantime, English wins:

```ts
const slow = i18n.setLocale('zh-CN')
const last = i18n.setLocale('en')
await last
// English is active even after the Chinese catalog arrives.
```

`preload(locale)` fetches a catalog without switching, for warming the other
language before the user asks for it. Concurrent requests for one locale share a
single load; a failed load is not cached, so a retry reaches the loader again.

## ICU messages

Plural and select use standard ICU MessageFormat:

```ts
// locales/en.ts
export const en = {
  'common.save': 'Save',
  'admin.users.count': '{count, plural, one {# user} other {# users}}',
  'admin.role': '{role, select, admin {Administrator} other {Member}}',
} as const

export type MessageKey = keyof typeof en
```

```ts
// locales/zh-CN.ts
export const zhCN = {
  'common.save': '保存',
  'admin.users.count': '{count} 位用户',
  'admin.role': '{role, select, admin {管理员} other {成员}}',
} satisfies Record<MessageKey, string>
```

Plural categories come from `Intl.PluralRules` for the target language, not from
`count === 1`. Chinese has one category, English has two; the same key renders
correctly in both without a special case in application code.

Do not build sentences by concatenation. `t('a') + count + t('b')` cannot be
translated: word order differs, and the plural form applies to a noun the second
fragment does not know about.

## Locale negotiation

```ts
resolveLocale('zh') // 'zh-CN' — the Playground's legacy value
resolveLocale('en-US') // 'en'
resolveLocale('zh-TW') // undefined — Traditional is not Simplified
negotiateLocale(['ja', 'zh-CN']) // 'zh-CN', in candidate order
```

`zh-TW`, `zh-HK` and `zh-Hant` deliberately do **not** map to `zh-CN`: showing
Simplified text to someone who asked for Traditional is worse than falling back
to a language they can at least recognise as foreign. They fall through to the
next candidate, or to `en`.

`applyDocumentLocale` mirrors the active locale onto `<html lang>`, which screen
readers use to pick a voice. It is on by default; pass
`syncDocumentLang: false` outside a document.

## Validation

`checkCatalog` compares a catalog against the reference key set and reports
missing keys, extra keys, empty values, and values copied verbatim from English.
`assertCatalog` is the throwing variant — `createI18n` runs it in strict mode
(the default) so a malformed catalog fails immediately in development.

`checkMessageSyntax` parses a message without formatting it, and
`messageArgumentNames` reads the compiled AST to compare placeholders across
locales:

```
en:     {count, plural, one {# user} other {# users}}   -> ["count"]
zh-CN:  {count} 位用户                                   -> ["count"]
```

The templates differ; the argument set must not. A Chinese message that drops
`{count}` renders the noun with no number, and no amount of type checking on the
key alone catches it.

CI runs `scripts/check/check-i18n.ts`, which applies all of the above to every
`locales/en.*` + `locales/zh-CN.*` pair in the repository.

## What must not be translated

Protocol values, error codes, user names, emails, file paths, model names,
provider IDs, API keys, audit records, chat message bodies, code, and diffs.
Translation is a display concern: a request still sends `status=active` after the
UI renders it as "活跃".

## Adopting it in an application

1. Add `locales/en.ts` as the source of truth; derive `MessageKey` from it.
2. Add `locales/zh-CN.ts` with `satisfies Record<MessageKey, string>`.
3. Create the instance once, at application setup, and pass it explicitly to the
   components that render text.
4. Replace literal strings with `i18n.t(key)`; move runtime state to
   `i18n.message(key, params)`.
5. Run the gate: `node --import tsx scripts/check/check-i18n.ts`.

Applications own their catalogs — the runtime ships no product copy.
