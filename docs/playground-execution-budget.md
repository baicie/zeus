# Playground 执行预算：能力边界与实测

日期：2026-11-13
基线：`origin/main` @ `7d1031e4`
相关：`docs/performance/rfc-babel-wasm-compile-chain.md`、`packages/devtools/playground-engine/src/preview.ts`

---

## 1. 两层保护，能力不同

Playground 的沙箱里有一层**代码注入**的预算和一层**宿主**的终止能力。
它们在"能不能真的停下来"这件事上完全不同，混为一谈会得出错误的结论。

| 层       | 机制                                       | 能在什么情况下停下       | 位置                                                                       |
| -------- | ------------------------------------------ | ------------------------ | -------------------------------------------------------------------------- |
| 代码注入 | 每个循环前捕获时间戳，体内比较 1000 ms     | 循环**主动回到判断点**时 | `packages/devtools/playground-engine/src/preview.ts` 的 `loopBudgetPlugin` |
| 宿主终止 | 请求超时后 `resetFrame()` 替换 iframe 元素 | 随时，**包括同步死循环** | `examples/playground-editor/src/preview.ts:84-120`、`:311-319`             |

## 2. 代码注入层能做什么

- 同步循环：每次迭代都会回到 `if (now - started > 1000) throw`，因此能被终止。
  实测 `while (true) {}`、`for (;;) {}`、`do {} while (true)`、无限 `for...of`
  全部在约 1 秒后抛出 `ZEUS_PLAYGROUND_LOOP_BUDGET`。
- 时钟不可被用户替换：时间戳函数在模块顶层用
  `performance.now.bind(performance)` 捕获一次，此后用户代码覆写
  `globalThis.performance.now` 或整个 `performance` 对象都不影响已捕获的引用。
  （`bind` 是必要的：`performance.now` 以 `performance` 为接收者，
  取出裸方法再用 `.call(otherThis)` 会抛 `Illegal invocation`。）
- 合法异步循环不被误杀：预算只统计**两次迭代回到判断点之间的实际耗时**。
  一个 `while (n < 8) { await sleep(200) }` 的循环累计等待 1.6 秒，
  但每次迭代本身的占用接近零，因此不会触发。

## 3. 代码注入层不能做什么

以下限制是**如实的**，不是可以通过调参回避的：

1. **无法中断不回到判断点的执行。** `while (true) {}` 每次迭代都会回去，所以能停；
   但一段不经过任何被插桩循环的长任务（例如一次巨大的递归、一个超大数组的
   同步 `map`）没有判断点。预算对它无效。
2. **它不是隔离。** 代码与用户代码在同一个 realm、同一个事件循环上。
   预算的效力依赖"用户代码没有破坏它引用的东西" —— 捕获时钟解决了最常见的
   破坏方式，但不是完整的安全边界。
3. **同事件循环上的 `setTimeout` 不能中断已阻塞的循环。** 这一点必须写明：
   如果用户代码在**宿主**页面的主线程上死循环，宿主的定时器永远不会触发。
   Playground 的设计把用户代码放在 iframe 里，正是为了避开这条。

## 4. 宿主终止层：实测

`resetFrame()` 用 `cloneNode(false)` + `replaceWith` 替换 iframe 元素。
替换会销毁 iframe 的浏览上下文，其中正在执行的脚本随之终止。

实测（Chromium，Playwright，2026-11-13）：

```
在 iframe 内运行 while (true) {}，等待 300 ms
宿主执行 cloneNode + replaceWith
→ 宿主主线程耗时 50 ms，未被阻塞
→ 替换后宿主仍响应（1 + 1 === 2）
```

**结论**：宿主对忙碌 iframe 的元素替换是**非阻塞**的，能终止同步死循环。
这提供了独立于用户执行线程的一层保护。

### 4.1 这一层的边界

- **只在宿主页面自己的事件循环上有效。** 如果宿主主线程自己被阻塞（不应发生 ——
  用户代码在 iframe 内），这层也不工作。
- **它终止的是整个预览，不是单个循环。** 用户体验是"预览被终止并重建"，
  而不是"那个循环停了、其他继续"。
- **它依赖 `resetFrame()` 被调用。** 当前由 `run()` 的超时定时器触发
  （`examples/playground-editor/src/preview.ts:104-112`），默认 3 000 ms、
  上限 10 000 ms。若用户代码在 iframe 内阻塞了**沙箱自己的**事件循环，
  沙箱无法自行回报，只有宿主超时会生效。

## 5. 结论

| 问题                             | 答案                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------- |
| 同步无限循环能被可靠中断吗？     | **能**，经由宿主 `resetFrame()`。实测非阻塞、有效                             |
| 只靠代码注入预算够吗？           | **不够**。它覆盖循环这一最常见的失控形态，但不是隔离                          |
| 需要重构沙箱才能提供强制终止吗？ | **不需要**。iframe 生命周期已经提供了；当前缺的是把它写成显式契约并有测试守着 |

**本轮不做沙箱重构。** 现有两层已能在真实浏览器里停下最坏情况；
把"宿主替换 iframe 必须能终止阻塞脚本"写成测试并纳入常规 CI（见
`scripts/playground/check-playground-loop-budget.ts`），比改造架构更有价值。

如果将来需要**单次执行**级别的强制上限（而不是整个预览重建），
那才需要 Worker + `terminate()` 或独立的进程边界，应另开 RFC。

## 6. 未测事项

- Firefox / WebKit 上"替换忙碌 iframe 是否同样非阻塞" —— 本轮只实测 Chromium。
- 沙箱 `postMessage` 往返在 iframe 被替换瞬间的行为 —— 由既有的
  `cancelPending(ZEUS_PLAYGROUND_PREVIEW_RESET)` 处理，本轮未加新测试。
- 长度超过 10 000 ms 上限的合法计算是否会被宿主超时打断 —— 属于产品取舍，
  不是缺陷，未测。
