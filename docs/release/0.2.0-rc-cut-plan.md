## 3. RC 证据契约

`check:rc-readiness` 需要两份绑定同一 HEAD 的证据：

- `rc-evidence.json`（`ZEUS_RC_EVIDENCE_FILE`）
- `pair.json`（`ZEUS_RELEASE_PAIR_FILE`）

R5 起 `rc-evidence.json` 为 `zeus.rc-evidence/v3`，由
`scripts/release/assemble-rc-evidence.ts` 从 Stage 2 在线验收、部署事务、provenance
和 release pair 生成；四个产品 URL 来自验收报告，不接受手写：

- `deployment.decision` 必须为 `ONLINE_ACCEPTED`，`transactionStatus` 为 `PASS`；
- `deployment.acceptanceSha256` / `transactionSha256` / `provenanceSha256` 绑定文件摘要；
- 每个产品的 `artifactDigest` / `imageDigest` 与部署事务一致；
- `crossPlatform` / `releaseApproval` 来自独立的 `rc-approval` artifact，commit 必须等于 Core HEAD。

证据必须来自真实部署验收，而不是手写 URL：

- `deployment-acceptance.json` 的 `decision` 必须为 `ONLINE_ACCEPTED`，四产品
  均为 `ONLINE_PASS`；
- 每个产品的 `artifactDigest` / `imageDigest` 必须与 Stage 2 的
  `deployment-transaction.json` 一致；
- `provenance.json` 的 Core/UI commit 必须等于 RC 源 commit；
- Playground 必须包含 sandbox CSP/opaque-origin 负向结果；
- Admin 必须包含 Session/Cookie/CSRF/viewer-403 结果；
- AI 必须是 `publicReplay=true` 的只读矩阵结果；
- 人工 A11y/审批字段只接受签名结果，未执行保持 `NOT_RUN`。

## 4. Cut 顺序

0. **准备变量**：`ZEUS_UI_REF`（对齐到 Core RC 的 UI 分支）、`ZEUS_UI_VERSION`、
   `ZEUS_DEPLOYMENT_EVIDENCE_RUN_ID`（Stage 2 在线验收 run）、
   `ZEUS_RC_APPROVAL_RUN_ID`（人工审批 artifact run）。
1. **冻结代码**：Core/UI RC PR 合并到各自 main，记录 tree SHA；禁止再改。
2. **Core RC 版本 commit**：`pnpm version:packages --version 0.2.0-rc.0`，同步
   Cargo/native loader/templates；提交后跑完整 `release:precheck --channel rc`。
3. **Core RC 发布**：`v0.2.0-rc.0` tag → release workflow → npm dist-tag `rc`；
   `latest` 不得指向 prerelease。
4. **UI 对齐与发布**：UI pin 到 Core `0.2.0-rc.0`，跑 UI aligned/CI/canary，
   发 `0.2.0-rc.0` 到 `rc`。
5. **四产品 RC 构建**：Stage 1 从两个 RC commit 构建，产物带 build-info 与
   image ID；Stage 2 在隔离环境完成事务演练与回滚演练。
6. **公网验收**：经明确批准后部署到 staging/production，生成
   `deployment-acceptance.json` + `deployment-transaction.json`。
7. **人工验收**：VoiceOver/NVDA、键盘、200% Zoom、DataGrid、Shadow DOM、
   AI SSE 播报、审批 Dialog、移动端；未执行项为 `NOT_RUN`。
8. **联合批准**：Core/UI/产品三方签署，`release:joint-readiness` 消费真实证据。
9. **正式 Tag/Release**：仅在以上全部 PASS 后创建；`npm publish`、dist-tag
   promotion、GitHub Release 都需单独授权。

### 5.1 证据装配命令

```sh
pnpm exec tsx scripts/release/assemble-rc-evidence.ts \
  --acceptance temp/deployment-evidence/deployment-acceptance.json \
  --transaction temp/deployment-evidence/deployment-transaction.json \
  --provenance temp/deployment-evidence/acceptance/provenance.json \
  --pair temp/deployment-evidence/acceptance/pair.json \
  --base temp/rc-approval/rc-evidence.base.json \
  --out temp/release

`rc-evidence.base.json` 由人工审批 artifact 提供：

  "releaseApproval": { "approver": "release-owner", "commit": "<core>" }
}
```

## 6. 回滚与失败重试

- **npm**：RC 发布后不覆盖已发布 tarball；坏包只能 deprecate 并发布新的
  `rc.N`。`latest` 永不回退到 prerelease。
- **Core/UI**：保留上一组 `0.1.1-beta.20` / `0.1.0-beta.34` 作为回滚目标；
  UI 精确 pin 必须与 Core 配对回滚。
- **部署**：Stage 2 保留旧容器与已验证 SQLite 备份；回滚后重新验收旧服务；
  禁止回滚到无 sandbox CSP 的 Playground 镜像。
- **Tag**：tag 创建失败/部分发布用 `retry-release-tag`，集合必须来自
  `zeusFixedPackages`，不得使用“全部非 ignore 包”。

## 7. 放行标准

RC Cut 只有在以下全部成立时才可标记 `RC_READY`：

- RC-01..RC-06 代码门禁关闭，P0 为零；RC-07 的 13 个 prerelease `latest`
  dist-tag 修复完成（使用受保护的 repair workflow 与 npm 授权）；
- `rc-evidence.json` 由已批准的 Stage 2 在线部署 run 和签名的 `rc-approval` artifact 生成；
- Core/UI CI、Native Matrix 7/7、packed consumers、canary 全绿；
- Stage 2 本地事务、失败回滚、并发互斥、备份恢复真实通过；
- 四产品 `deployment-acceptance` 为 `ONLINE_ACCEPTED`，AI 为只读 public replay；
- 人工 A11y 与联合发布审批已签署；
- 维护者明确授权 npm publish / dist-tag / Tag / Release。

在此之前，允许的状态只有 `BLOCKED_BY_CODE`、`BLOCKED_BY_SECURITY`、
`BLOCKED_BY_CI` 或 `BLOCKED_BY_ENVIRONMENT`。
