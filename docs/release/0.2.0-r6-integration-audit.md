### 2.3 B-6：视觉门禁的两次静默跳过

修复过程本身暴露了这个缺陷的两种形态，都来自运行日志：

```text
# 第一次：BASE 为空
BASE:
changed files:
##[notice]visual gate skipped: no AI Workbench change

# 第二次：PR 被当作 push，只比了最后一个 commit
EVENT: push
changed files in the pushed commit range:
##[notice]visual gate skipped
```

`workflow_call` 不传递 `github.event.pull_request.base.sha`。第一次读成空串，`git diff "" HEAD` 无输出；第二次退回 `HEAD~1`，只覆盖最新一个 commit，一个只改 yml 的后续提交就藏掉了它之前的 Workbench 改动。

### 2.4 C-7：三引擎焦点实测

```text
chromium  IN:BUTTONConfirm IN:BUTTONCancel IN:BUTTONConfirm ...
firefox   IN:BUTTONConfirm IN:BUTTONCancel IN:BUTTONConfirm ...
webkit    OUT:INPUT OUT:INPUT OUT:TEXTAREA OUT:DIVName OUT:DIVTeam ...
```

WebKit 从第一次 Tab 就离开对话框。原因是陷阱只监听 panel 上的 `keydown`，而 Safari 在 panel 持有焦点后把 Tab 的 keydown 投递给文档中的下一个元素。

### 2.6 C-8 / C-9：原判定撤回

**先前的结论是错的，这里明确撤回。**

上一轮把这两个缺陷记账为：

> `open` 被反射成宿主属性后读回为 `true`，组件无法区分"读者关掉了"与"属性还在"。
> 于是 Escape 不关闭（C-8），关闭一次后再也打不开（C-9）。

按这个机制去复现，复现不出来。用真实 Admin 链（真实 `dist` + 真实 server + Admin 实际安装的
beta.34）在三个引擎上跑完整序列，结果如下：

| 引擎     | 打开 | Escape               | 重开 | 关闭按钮 | 再重开 | 遮罩 | 再重开 |
| -------- | ---- | -------------------- | ---- | -------- | ------ | ---- | ------ |
| Chromium | ✓    | ✓                    | ✓    | ✓        | ✓      | ✓    | ✓      |
| Firefox  | ✓    | ✓                    | ✓    | ✓        | ✓      | ✓    | ✓      |
| WebKit   | ✓    | 仅焦点仍在面板内时 ✓ | ✓    | ✓        | ✓      | ✓    | ✓      |

也就是说，属性残留并不会让组件卡在 `open`。真实存在的缺陷是下面三条，根因全部不同：

**一、未受控对话框会把自己变成受控的。**
`getOpen()` 每次读取都重新判断 `props.open !== undefined`，而 `setOpen()` 的第一件事就是
写 `ctx.host.open`。于是**触发器第一次点击自己写出了这个 prop**，下一次读取看到它，组件就把
自己判定成受控——从此只发事件、不再应用状态。表现是"关不掉"，和原记录的症状相同，机制不同。

更糟的是投影重建：Zeus 会在 light-DOM 重建后重新执行 setup，此时 `props.open` 已经是组件自己
写的值，`props.open !== undefined` 恒为真。

**二、受控对话框会覆盖 owner 给它的值。** `setOpen` 无条件写 `ctx.host.open`，受控时也一样。
owner 的渲染和组件的写入互相打架。

**三、焦点移动只覆盖组件自己发起的路径。** 焦点写在 `setOpen` 里，所以 `el.open = true`、
路由恢复状态、受控 owner 重新渲染这三条路径都不会搬焦点——模态打开后焦点仍停在背后的页面上。

**修复**（`fix/dialog-state-and-focus`，zeus-ui）：

- 受控与否在 setup 时判定一次，并记录在元素上（`Symbol.for('@zeus-web/dialog/state')`），
  重建后的 setup 继承它，不再重新推导；
- 受控时只 `emit`，不写 prop；未受控时才应用并发布 `open`；
- 焦点跟随 open 状态而非调用路径；
- Escape 与 Tab 陷阱移到 `document`：面板级监听只能在焦点已经进面板时听到按键，而要紧的恰好
  是焦点不在里面的那些情况；
- 一次 Escape 只关一层（跨 bundle 共享的已消费登记表，而不是 `stopImmediatePropagation`，
  后者会连带静默页面自己的监听）；
- 焦点候选过滤掉无盒子、`inert` 祖先、`visibility: hidden` 的控件；
- 已脱离文档的宿主不再应答事件。

**证据**：`pnpm check:dialog-interaction`（zeus-ui）以真实包构建在 Chromium / Firefox / WebKit
上跑 18 步，三引擎全绿，**无任何引擎豁免**。Admin 侧 `check:admin` 的 Escape / 重开 / 焦点
恢复断言同样三引擎全绿（见 §6.5 的 C-7 行）。

### 2.7 E-3：切换语言会抛响应式错误

补齐语言断言后，`check:admin` 立刻失败：

```text
Error: expect(received).toEqual(expected)
+ "A reactive effect cannot synchronously update its own dependencies. Move the
   write to an event or a separate effect."
```

原因在 `examples/admin/src/app.tsx`：负责应用账号语言偏好的 effect 先读
`i18n.locale()`（这使它成为依赖），再调 `setLocale`——effect 同步写自己刚读过的依赖，
Zeus 直接抛错。这个 throw 落在设置页的语言切换上：写入触发 effect 重跑，重跑又看到不一致，
再写一次。

此前没有任何测试切换过语言，所以这个错误从未被看到。**R6-E 第 11 项要求验证的正是这件事。**

修法是排序而不是抑制：比较保留（它避免每次会话刷新都重写），但写入排到 effect 返回之后。
`queueMicrotask` 在绘制前执行，界面不闪烁；回调执行时重新读取偏好与当前 locale，
避免覆盖期间发生的会话更新。

## 6.5 独立审查发现的额外缺陷

四个工作流完成后做了一轮独立对抗审查（每个区域一位 reviewer，每条发现由独立 agent 尝试反驳）。发现的缺陷按"修复 → 证据"记录如下。

### R6-A 区域

| 编号 | 级别   | 问题                                                                                                                                                                                                                                       | 状态                                      |
| ---- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------- |
| A-6  | **P1** | AI Demo 的 `coreCommit` 不是真正构建它的 Core 提交。Workbench 依赖 npm 上锁定的 `@zeus-js/zeus 0.1.1-beta.20`（tag `7fc50515`，比检出的 Core 落后 157 个提交），而清单把检出 SHA 记成了它的 `coreCommit`——正是 R6-A 要消灭的缺陷换了个字段 | 已修：新增 `aiRuntime` 字段               |
| A-7  | P2     | `product in DEMO_PRODUCTS` 沿原型链，`'toString'` 能绕过未知产品检查，随后在校验时抛 TypeError                                                                                                                                             | 已修                                      |
| A-8  | P2     | 没有检查要求 `coreCommit != uiCommit`——单一 SHA 冒充两仓库恰是原始缺陷的形状                                                                                                                                                               | 已修                                      |
| A-9  | P2     | `siteDigest` 的文件排序用 `localeCompare`，digest 依赖宿主 locale                                                                                                                                                                          | 已修（`build-info.ts`，缺陷先于本轮存在） |
| A-10 | P2     | `--verify`（不带 `--reproducible`）不校验 metadata schema                                                                                                                                                                                  | 已修                                      |
| A-11 | P2     | publish 作业的跨 job 复验是自指的，不比对 site 内清单的 commit 字段                                                                                                                                                                        | **未修**                                  |
| A-12 | P2     | 「同一对 SHA 可复现」的表述超出证据：录制内嵌真实时间戳与 UUID，同一配对每次构建的产物 digest 不同                                                                                                                                         | **未修**（表述已在 §4.1 收紧）            |

A-12 需要说清楚：`--reproducible` 证明的是「给定同一棵树，清单的生成是确定的」，不是「同一 SHA 组合能产出字节相同的 Demo」。后者对含实时录制的构建不可能成立，把它写成可复现会误导。真正的保证是：双侧 SHA 正确、产物 digest 绑定当次实际构建、任一字节变化都会被检出。

### A-6 的证据

```text

  7fc5051590a9c4d0b93f6d7fac1b9f2d46751ab3
git rev-parse origin/main
  d7c82cfdd71efba1e3b84505e0414c3d1e1e94e3
```

修复前的清单同时声称 `coreCommit: d7c82cfd…` 并给出 digest——用 digest 为一条不实陈述背书，比原来的缺陷更难被发现。

### 7.7 尝试过并失败的方案

**把构建产物提交到 `vendor/`。** 为了让 Admin 不依赖新发布就能验证，一度把
`0.1.0-beta.35-local.1` 的构建复制进 `vendor/zeus-web-dialog` 并由 `examples/admin/package.json`
以 `file:` 引用。本地 `check:admin` 三引擎全绿，**CI 上失败**：

```text
src/gallery.tsx(37,36): error TS2307: Cannot find module '@zeus-web/dialog/wc'
```

根因：仓库 `.gitignore` 忽略 `dist`，所以只有 `package.json` 和 `README.md` 进了提交，
vendored 包没有代码。这类失败只在 CI 暴露，正是本次要消灭的模式，因此整套回退。

替代方案是 `pnpm admin:link-dialog`：从相邻 zeus-ui 检出构建、连同 runtime peer 一起装进
`examples/admin/node_modules`，`--restore` 用 pnpm 装回发布版。它**不写入仓库**，因此不伪装成
发布版本；它证明的是集成，不是发布。
