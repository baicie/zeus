## 二、阻塞 RC 的三件事

### 2.1 UI 候选 `ca8cf2c8` 不可用

`ca8cf2c8` 的 `examples/ai-workbench/package.json` 仍是：

```json
"@zeus-js/runtime-dom": "0.1.1-beta.20",
"@zeus-js/zeus": "0.1.1-beta.20",
```

`#149` 修了检测，但没修这个文件。需要一个新 commit 把两处切到 `0.2.0-rc.0`，并重新生成 `pnpm-lock.yaml`。

**这必须在 Core 发布之后做**，因为锁文件要对着 registry 里的真实 RC 解析。

### 2.2 `pnpm-lock.yaml` 无法在发布前存在于 main

对隔离 registry 生成的锁文件是**有效**的（§3.7：15 条 integrity 全部一致）。但它不能先于 Core 发布进入 main——`pnpm install --frozen-lockfile` 会失败，而这是正确行为。

所以顺序是：Core 发布 → UI 切 pins + 生成锁文件 → UI PR。

### 2.3 Tag ruleset 已配置，但未在真实发布路径验证

用一次性 ref 验证了三条规则都生效，44 个真实 tag 未受影响。但真实 `v0.2.0-rc.0` 推送时的行为未被验证过——只能等第一次真实发布。

## 三、首次 0.2.0-rc.0 Cut 的完整顺序

### Phase 0：前置检查

```bash
# Core main 上的版本与配对目录
cd zeus && git fetch origin && git log --oneline -1 origin/main
ls release-pairing/          # 应只有 README.md

# UI main 的版本
cd ../zeus-ui && git log --oneline -1 origin/main
grep -m1 '"version"' package.json    # 应仍是 0.1.0-beta.35
```

### Phase 1：Core 版本切换（独立 PR）

在 Core 的一个分支上：

```bash
git checkout -b release/0.2.0-rc-bootstrap origin/main
pnpm install --frozen-lockfile

# 切版本
pnpm exec tsx scripts/release/version-rehearsal.ts --version 0.2.0-rc.0 --apply

# 同步 native loader（rehearsal 不调用它，必须手动）
pnpm exec tsx scripts/release/sync-native-loader.ts 0.2.0-rc.0

# 验证
grep -c '0.2.0-rc.0' packages/core/compiler-native/index.js   # 应为 52
grep -m1 '"version"' packages/devtools/vite-plugin/package.json  # 应为 0.0.5
pnpm exec tsx scripts/release/create-zeus-versions.ts --check
```

写 bootstrap 配对记录 `release-pairing/v0.2.0-rc.0.json`：

```json
{
  "schema": "zeus.release-pairing/v1",
  "coreVersion": "0.2.0-rc.0",
  "uiCommit": null,
  "uiVersion": "0.2.0-rc.0",
  "verifiedAt": "<ISO-8601 UTC>",
  "bootstrap": true,
  "firstPublish": [
    "@zeus-js/i18n",
    "@zeus-js/eslint-plugin",
    "@zeus-js/playground-engine"
  ]
}
```

提交、开 PR、等 CI 全绿、合并。

### Phase 2：打 Tag

```bash
# 在合并后的 main 上确认
git checkout main && git pull --ff-only
grep -m1 '"version"' package.json    # 0.2.0-rc.0
cat release-pairing/v0.2.0-rc.0.json # bootstrap: true, uiCommit: null

# 建 tag（这会触发 release.yml）
git tag v0.2.0-rc.0
git push origin v0.2.0-rc.0
```

`release.yml` 会：读 bootstrap 记录 → 跳过 UI checkout → precheck → 授权（`POLICY_LIMITATION`，不阻塞）→ 发布 → 验证 → `check:latest-tags`。

**必须确认的**：`check:latest-tags` 会报三个首发包的 `latest` 污染。这是已知并接受的。

### Phase 3：修 latest（发布后立即）

```bash
pnpm exec tsx scripts/release/cleanup-native-latest.ts --apply   # 若涉及
# 或
pnpm repair:latest-tags --apply
```

读回验证，因为 `npm dist-tag rm` 可能退出 0 而 `latest` 仍在（已对 Verdaccio 实测）。

### Phase 4：UI 版本切换（独立 PR）

Core 发布后，`@zeus-js/*@0.2.0-rc.0` 已存在于 npmjs。

```bash
cd zeus-ui
git checkout -b release/0.2.0-rc-pair origin/main

# 切所有 @zeus-js pins（含 examples/）
# 这一步必须覆盖全部 4 个 workspace 组 —— #149 修的正是这个
```

切完 `examples/ai-workbench` 后：

```bash
pnpm install --no-frozen-lockfile     # 对着真实 registry 生成锁文件
grep -c "registry.npmjs.org" pnpm-lock.yaml   # 记录数量供 review
pnpm check:release-pairing --version 0.2.0-rc.0 --release-sha <commit>
```

提交、开 PR、等 CI、合并。

### Phase 5：写配对记录（Core，第二个 PR）

**这一步不能早于 Phase 4 合并**，因为记录要写 UI 候选的 SHA。

```bash
cd zeus
git checkout -b release/0.2.0-rc-pair-record origin/main
```

把 `release-pairing/v0.2.0-rc.0.json` 从 bootstrap 改成配对：

```json
{
  "schema": "zeus.release-pairing/v1",
  "coreVersion": "0.2.0-rc.0",
  "uiCommit": "<Phase 4 合并后的 commit SHA>",
  "uiVersion": "0.2.0-rc.0",
  "verifiedAt": "<ISO-8601 UTC>",
  "firstPublish": [
    "@zeus-js/i18n",
    "@zeus-js/eslint-plugin",
    "@zeus-js/playground-engine"
  ]
}
```

验证：

```bash
pnpm check:release-pairing --online
```

提交、开 PR、合并。

**注意**：这个记录不重指 `v0.2.0-rc.0` tag。tag 仍指向 bootstrap commit。记录是给**审计**看的，说明"Core 0.2.0-rc.0 与 UI commit X 配对验证过"。这是 Bootstrap → Pair 的设计：tag 不可移动，配对通过独立记录表达。

### Phase 6：UI 发布

```bash
cd zeus-ui
# 确认 main 上是 Phase 4 的 commit
gh workflow run release.yml --ref main \
  --raw-field version=0.2.0-rc.0 \
  --raw-field tag=rc
```

`release.yml` 会：`--online` 校验 Core tag 与记录 → 打 UI tag → dispatch publish → publish.yml 再次 `--online` 校验。

## 四、这个顺序为什么成立

每一步的输入都在使用前存在：

| 步骤               | 需要                              | 何时存在         |
| ------------------ | --------------------------------- | ---------------- |
| Phase 2 打 tag     | bootstrap 记录在 commit 内        | Phase 1 合并后   |
| Phase 2 发布       | 无 UI commit                      | bootstrap 不要求 |
| Phase 4 切 pins    | `@zeus-js@0.2.0-rc.0` 在 registry | Phase 2 之后     |
| Phase 4 生成锁文件 | 同上                              | 同上             |
| Phase 5 写记录     | UI commit SHA                     | Phase 4 合并后   |
| Phase 6 UI 发布    | Core tag + 记录可读               | Phase 5 之后     |

没有任何一步需要未来才存在的东西。

## 五、与旧 README 的差别

旧 README 的顺序是「Core 发布 → UI 切 pins → Core 记录」。#309 已删除它，因为第 1 步的 tag 会指向没有记录的 commit，workflow 在发布前就失败。

新顺序把「记录」拆成两个身份：

- **Phase 1 的记录**：bootstrap，声明未配对，让 tag 能被打出来
- **Phase 5 的记录**：配对，声明已验证，让 UI 能发布

同一个路径，两次写入，中间隔一次真实发布。tag 只打一次。
