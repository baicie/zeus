## 3. minimatch：尝试后回退

强升 11.0.9 会让 lint 完全起不来：

```
SyntaxError: The requested module 'minimatch' does not provide an export named 'makeRe'
    at eslint-plugin-import-x/lib/rules/no-internal-modules.js:1
```

`eslint-plugin-import-x@4.16.2` 声明 `minimatch: ^9.0.3 || ^10.1.2`，而 10.x 全部仍在
`>=7.0.0 <11.0.1` 范围内。**没有既不破坏 eslint 又消除该 advisory 的版本。**

保留在 moderate（低于 `--audit-level=high` 阈值），不做破坏性强升。这符合「禁止
无依据地使用 overrides 强行升到不兼容版本」。

唯一路径是 `examples__stencil-wrapper>@stencil/react-output-target>ts-morph`，不在
发布包闭包内。

## 4. picomatch：风险接受

见 `docs/release/2026-11-18-picomatch-risk-acceptance.md`。

### 关键事实

| 项           | 值                                                 |
| ------------ | -------------------------------------------------- |
| 修复版本     | **不存在**（`patched: <0.0.0`，最新即 4.0.7）      |
| 实测复现     | `picomatch('+(*a)')('a'.repeat(30))` → **7777 ms** |
| 默认模式     | 最坏 3 ms                                          |
| 仓库内使用点 | 1 处（`componentTransformFilter.ts:16-17`）        |
| 模式来源     | `vite.config.ts` 或内置默认值                      |

### 为什么可接受

攻击需要控制 glob 模式。控制模式的人就是控制 `vite.config.ts` 的人，而那个人本来
就在构建时执行任意代码。**不存在跨信任边界的路径。**

### 边界

- 只豁免 `CVE-2026-112366`，其他任何 high/critical 仍然阻断；
- `--audit-level=high` 不变；
- 审计输出打印 `3 high (1 ignored)`，豁免可见；
- 上游发布 `>=4.0.8` 时立即升级并删除记录。

## 5. rc.1 Recovery 的安全边界

`bootstrap-eligibility` 原本硬编码 `sequence === '0'`，rc.1 必然被拒。恢复路径
**比普通 bootstrap 更严格**：

| 条件                             | 不满足时                         |
| -------------------------------- | -------------------------------- |
| 必须是紧邻的前一个 RC            | 拒绝——rc.2 不能蹭 rc.0 的失败    |
| 失败 run 从同一 commit 启动      | 拒绝——否则归因到错误的 tag       |
| 失败 run 在任何 publish 之前停止 | 拒绝——部分发布无法用再发一版恢复 |
| rc.0 不在 registry               | 拒绝                             |
| rc.1 不在 registry               | 拒绝                             |
| 该线无其他已发布 RC              | 拒绝                             |
| rc.0 无配对证据                  | 拒绝                             |
| Registry 可查询                  | 拒绝                             |

### 证据不来自文件

记录只声明「查哪个 run」。事实从 GitHub 读：

- tag 是否解析到记录声称的 commit
- run 是否从那个 commit 启动
- run 里有没有 publish 步骤启动或完成

测试专门验证：记录里写 `failedRunReachedPublish: true` 时，
`readRecoveryClaim` **不返回该字段**——那正是攻击者会翻的那个。

`skipped` 的 publish 步骤算「未到达」；`failure` 或 `completed` 都算「已到达」，
因为「可能发过」就是拒绝理由。

## 6. 隔离 Registry 恢复演练

真实 Verdaccio 6 + 真实产物 + 真实发布路径。

### 方法：先建基线

空 registry 上每个包都是首发，发 32 个 RC 会得到 32 个污染 `latest`——与真实
npmjs 不符。先发 29 个稳定版再发 RC。

### 结果

```
PASS recovery-claim: recovers 0.2.0-rc.0
PASS manifest: 32 publishable, 3 first publication(s)
PASS registry-present: 32 of 32 present
PASS latest-policy: ACCEPTED_DEVIATION (3 accepted, 0 refused, 0 unknown)
PASS first-publish-deviation: exactly the 3 approved package(s) deviate

latest at 0.2.0-rc.1: 3 | at a stable version: 29
```

### 负向

| 场景       | 结果                         |
| ---------- | ---------------------------- |
| 无批准名单 | `REFUSED`，退出 1            |
| 有批准名单 | `ACCEPTED_DEVIATION`，退出 0 |

**这是本地模拟，不是生产发布证据。** 报告带 `source: 'local-simulation'` 和
`productionPublished: false`。
