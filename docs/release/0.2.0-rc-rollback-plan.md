# Zeus 0.2.0 RC 回滚方案

## 0. 回滚的分级

不是所有动作都能回滚到"什么都没发生"。按可逆性分三级：

| 级别            | 含义                           | 涉及对象                                                  |
| --------------- | ------------------------------ | --------------------------------------------------------- |
| **A. 完全可逆** | 执行后可以精确恢复到执行前状态 | 版本号、Tag、Pages、镜像部署、环境变量                    |
| **B. 部分可逆** | 可以缓解，但会留下痕迹         | 镜像推送（旧 tag 仍在，但新 tag 已写）、公告              |
| **C. 不可逆**   | 无法撤回，只能标记或等待       | **npm 发布**（72 小时内可 unpublish，之后只能 deprecate） |

RC 判定必须考虑：第 5 步（npm 发布）属于 C 级，一旦执行就承担了下游安装者已拉取的风险。

---

## 1. 版本号切版回滚（A 级）

**场景**：切到 `0.2.0-rc.0` 后发现问题，需要退回 `0.1.1-beta.20` / `0.1.0-beta.35`。

```bash
# Core
git revert <version-commit>
# UI
git revert <version-commit>
```

**注意**：

- 切版会改动 78 个 `package.json` + `pnpm-lock.yaml` + `Cargo.toml` + native loader。
  `revert` 会同时回退这些，不需要手工修。
- 如果已经运行过 `syncNativeLoader`，`packages/core/compiler-native/index.js` 里的版本号也会被
  revert 带回。**验证方式**：`grep -r "0.2.0-rc.0" packages/ | wc -l` 应为 0。
- 如果切版后已经发布过 npm，**不能**只 revert 版本号——npm 上的版本还在。

**验证**：`pnpm check:package-versions` 应输出原版本对齐。

## 2. Tag 回滚（A 级）

```bash
git tag -d v0.2.0-rc.0
git push origin :refs/tags/v0.2.0-rc.0
```

**注意**：如果该 Tag 已被 `release.yml` 消费并生成了 artifact，删除 Tag 不会删除 artifact。
先确认发布工作流是否已运行。

## 3. npm 发布回滚（C 级，最高风险）

npm 发布是**唯一不能完全撤回**的动作。

### 3.1 72 小时内

```bash
npm unpublish @zeus-js/zeus@0.2.0-rc.0
```

**代价**：

- npm 对 `unpublish` 有限制（包 72 小时内、且不能有依赖它的已发布版本）
- 已安装该版本的消费者会拿到 404
- Core 32 个包 + UI 46 个包需要逐个处理，其中任何一个被其他已发布包依赖就失败

### 3.2 超过 72 小时

只能 deprecate：

```bash
npm deprecate "@zeus-js/*@0.2.0-rc.0" "Superseded: use 0.2.0-rc.1"
```

`deprecate` 不会阻止安装，只是警告。**消费者仍可能装到有问题的版本。**

### 3.3 推荐做法

发布 `rc.1` 而不是撤回 `rc.0`。这是 npm 生态的通行做法，也是本仓库 `skipExisting: true`
配置隐含的策略（发布器不会覆盖已存在的版本）。

## 4. dist-tag 回滚（A 级）

**场景**：`latest` 被 RC 污染。

```bash
# Core 提供了修复脚本
pnpm repair:latest-tags --apply
```

**背景**：仓库已知的问题是——npm 在发布某包**第一个版本**时会自动把 `latest` 指向它。
`@zeus-js/playground-engine`、`@zeus-js/eslint-plugin` 是本次首次发布，它们的 `latest`
会被写成 `0.2.0-rc.0`。

**必须**：发布后立即运行 `pnpm check:latest-tags`，非绿则立即 `repair:latest-tags --apply`。
这是 §8 操作清单第 6 步，不是可选步骤。

## 5. GitHub Pages 回滚（A 级）

```bash
# 在 zeus-demos 仓库
git revert <demos-commit>     # 保留历史，推荐
# 或
git reset --hard <previous>   # 去掉历史，不推荐
```

**当前回滚目标**：`f7603193`（上一次发布）。

**注意**：

- Pages 的配对元数据是"这两次提交"的唯一公开证据。回滚后该证据指向旧配对。
- **必须同时更新发布记录**，否则第三次验证会看到不一致的配对，误判为缺陷。
- CDN 可能有缓存，回滚后需等待或手动刷新。

## 6. Admin Image 回滚（A 级）

```bash
# 重新部署上一个不可变 tag
docker pull ghcr.io/baicie/zeus-admin:sha-<previous-commit>
# 或用 TCR 内网地址（更稳）
```

**为什么用 `sha-` tag 而不是 `main`**：`main` 是移动 tag，回滚时它可能已经指向新镜像。
`sha-<commit>` 是不可变审计点。

**验证**：

```bash
curl -s https://<admin-host>/build-info.json | jq '{coreCommit, uiCommit, artifactDigest}'
```

应与回滚目标一致。

**已知陷阱**：

- 旧容器可能属于另一个 compose 项目
- Caddy 指向的端口可能与新容器不同
- **Caddyfile 是单文件挂载，必须原地覆盖；`sed -i` 会静默失效**

## 7. AI Workbench Image 回滚（A 级）

同 Admin Image。回滚目标为上一个 `sha-<ui-commit>`。

注意 AI Workbench 依赖 `/ai-host/` 的 nginx 代理（服务端注入 `Authorization: Bearer`），
回滚镜像时若 Host 也变了，需要一并确认代理配置。

## 8. Playground 回滚（A 级）

- **Pages**：revert 站点仓库
- **Image**：重新部署旧 `sha-` tag

## 9. 远程部署回滚（A/B 级）

```bash
# 事务回滚
pnpm tsx scripts/release/deployment-transaction.ts --rollback <transaction-id>

# 工作区恢复
pnpm tsx scripts/release/deployment-workspace-restore.ts
```

**已知陷阱**（历史记录，仍然适用）：

- `ssh` 空的位置参数会被丢弃，导致后续参数左移，报错像网络故障而实际是参数错位
- Caddy admin API 改不了 upstreams，只能改文件
- TCR 密码末尾句号曾导致 7 轮失败

## 10. Demo pairing 回滚（A 级）

**场景**：发现 `demo-pairing.json` 的 `coreCommit`/`uiCommit` 与实际构建不符。

```bash
# 本地验证
node --import tsx scripts/release/demo-pairing.ts --site <dir> --verify --reproducible \
  --core-commit <sha> --ui-commit <sha> --core-version <v> --ui-version <v>
```

若不通过，站点必须回滚到上一配对，并**记录为何配对失败**。

**本轮已确认**：最新配对 `core 69f494f2 + ui 89fc93ca` 与冻结 SHA 一致，无需回滚。

## 11. 回滚决策树

```
发现问题
  │
  ├─ 只在仓库内（未发布、未部署）
  │    └─ git revert，A 级，无外部影响
  │
  ├─ 已部署镜像 / Pages，未发布 npm
  │    └─ 回滚 tag / revert 站点，A 级
  │         └─ 用户影响：短暂不可用或回到旧版本
  │
  └─ 已发布 npm
       ├─ 72 小时内 → unpublish（C 级，会破坏已安装者）
       └─ 超过 72 小时 → deprecate + 发 rc.1（C 级，无法真正撤回）
```

## 12. 回滚的验证要求

每次回滚后必须验证，不能假定成功：

| 回滚对象      | 验证方式                                                                  |
| ------------- | ------------------------------------------------------------------------- |
| 版本号        | `pnpm check:package-versions`                                             |
| npm           | `npm view @zeus-js/zeus@0.2.0-rc.0 version`（应 404 或带 deprecate 标记） |
| dist-tag      | `pnpm check:latest-tags`                                                  |
| Pages         | 拉取站点，核对 `demo-pairing.json` 的 SHA                                 |
| Image         | `curl .../build-info.json` 核对 `coreCommit`/`uiCommit`                   |
| 远程部署      | `deployment-acceptance.ts`                                                |
| native 二进制 | `pnpm check:native-binaries`                                              |

## 13. 回滚的授权

**回滚本身也是生产操作**，同样需要维护者显式授权。

本文件只描述方法，不授权任何一条执行。特别是：

- 回滚 npm 的影响面超过发布本身（已安装者拿到 404）
- 回滚 Pages 会让唯一的公开证据回退
- 回滚镜像需要确认容器与 Caddy 的端口一致

## 14. 本轮是否需要回滚

**建议：不回滚。**

上一版此处写「两次部署的配对元数据都正确」，该表述**已被证伪**：

| 站点                      | coreCommit | uiCommit（记录） | 产物实际是否正确             |
| ------------------------- | ---------- | ---------------- | ---------------------------- |
| `admin.moonbyte.top`      | `69f494f2` | `ffde5592` ❌    | **正确**（chunk 含修复标记） |
| `playground.moonbyte.top` | `69f494f2` | `ffde5592` ❌    | 正确                         |
| `ai.moonbyte.top`         | `a648a4a1` | `89fc93ca` ✅    | 正确                         |

**产物是对的，记录是错的。**

回滚会把正确的产物换掉，不解决任何问题——反而会让线上失去对话框修复。
需要修的是 `build-info.json` 的 `uiCommit` 来源，不是重新部署。

| 动作               | 建议                 | 理由                                |
| ------------------ | -------------------- | ----------------------------------- |
| 回滚 Admin         | **否**               | 线上含修复，回滚会丢                |
| 回滚 Playground    | **否**               | 同上                                |
| 回滚 Demos Pages   | **否**               | 配对正确                            |
| 重新部署           | **需授权，但不紧急** | 应在修好 `vars.ZEUS_UI_COMMIT` 之后 |
| 修 `uiCommit` 溯源 | **是**               | 见部署事件文档 §7                   |

流程合规性方面：两次部署均有维护者合并授权在先，**不存在未授权部署**。
上一版「发生在不部署指令仍有效期间」的表述已撤回。

本文件仍不代为决定任何回滚执行——回滚本身是生产变更，需维护者显式授权。
