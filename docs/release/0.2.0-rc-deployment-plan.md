# Zeus 0.2.0 RC 部署计划

本文件描述**部署面是什么样**，不是授权部署。任何一项执行前，维护者必须逐条显式授权，
见 §8 的操作清单。

## 0. 核心事实：合并 main 就会部署

这一条必须放在最前面，因为本轮已经因为忽略它而发生了两次未经事前确认的生产变更。

三个工作流都以 `push: branches: [main]` 为触发条件，且路径过滤包含 `packages/**`：

| 工作流                            | 触发           | 路径过滤含 `packages/**` |
| --------------------------------- | -------------- | ------------------------ |
| `demos-pages.yml`                 | `push: [main]` | 是                       |
| `admin-image.yml`                 | `push: [main]` | 是                       |
| `playground-pages.yml`            | `push: [main]` | 是                       |
| `ai-workbench-image.yml`（UI 仓） | `push: [main]` | 是（`packages/*`）       |

**结论：任何一次把包含包改动的分支合并到 main，都会自动部署。** 不存在"只合并不部署"的路径，
除非同时修改工作流或使用 `[skip ci]` 之类的非常规手段（本轮不使用）。

## 1. GitHub Pages（`zeus-demos`）

| 项           | 值                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------- |
| 工作流       | `.github/workflows/demos-pages.yml`                                                            |
| 触发事件     | `push: main`（路径过滤命中）；`workflow_dispatch`（`publish` 输入，默认 `false`）              |
| 需要的权限   | `contents: read`；跨仓库推送用 `demos-pages` environment 内的凭据                              |
| 是否自动部署 | **是**（push 到 main 时 `if: github.event_name == 'push' \|\| inputs.publish == true`）        |
| 发布对象     | 分支（`zeus-demos` 的默认分支），不是 Tag，不是 digest                                         |
| 健康检查     | 构建后 `--verify --reproducible` 校验配对；发布前重新核对 `coreCommit`/`uiCommit`/`siteDigest` |
| 回滚方式     | 在 `zeus-demos` 仓库 `git revert` 到上一个 `demos: core … + ui …` 提交，或 reset 到它          |
| 失败恢复     | 构建失败 → publish job 不执行，站点保持上一版本；发布失败 → 同上                               |
| 对用户的影响 | 演示站点（Admin + AI Workbench 的只读 demo）更新或保持不变                                     |

**当前状态**：已发布 `demos: core 69f494f2… + ui 89fc93ca…`，与冻结 SHA 一致。回滚目标为
`f7603193`（上一次发布）。

**注意**：`zeus-demos` 的配对元数据是"这两次提交"的唯一公开证据。回滚站点会让该证据回退到旧配对，
因此**回滚 Pages 必须同时记录原因**，否则第三次验证会看到不一致的配对。

## 2. Admin Image

| 项           | 值                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------- |
| 工作流       | `.github/workflows/admin-image.yml`                                                                            |
| 触发事件     | `push: main`；`workflow_dispatch`（`deploy` 输入）                                                             |
| 需要的权限   | `contents: read`、`packages: write`；deploy job 使用 `environment: production`                                 |
| 是否自动部署 | **是**（`push: main` → `should_deploy=true`）                                                                  |
| 发布对象     | **三个 tag**：`main`（移动）、`sha-<commit>`（不可变审计点）、`YYYY.MM.DD-HHMM`                                |
| 健康检查     | 部署后由 `deploy` job 验证 revision；镜像内含 `build-info.json`（含 `coreCommit`/`uiCommit`/`artifactDigest`） |
| 回滚方式     | 重新部署上一个 `sha-<commit>` tag；或 `deployment-transaction.ts` 的事务回滚                                   |
| 失败恢复     | 构建失败 → 不推送、不部署，生产保持上一镜像；部署失败 → 同上，需人工确认容器状态                               |
| 对用户的影响 | Admin 应用（生产）重启或不变                                                                                   |

**当前状态**：run `43568170616` 在 `69f494f2` 上 `Deploy: success`、`Mirror to TCR: success`。

**已知风险**：该镜像内的 Admin 消费 `vendor/zeus-web-dialog`（本地构建，非 npm 发布）。
镜像能构建成功，是因为 `.dockerignore` 已加例外。但**这意味着一份生产镜像里含有未发布的代码**，
这是 RC 判定的阻塞项之一（见 readiness §5）。

## 4. Playground

| 项           | 值                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------- |
| 工作流       | `.github/workflows/playground-pages.yml`（Pages）、`.github/workflows/playground-image.yml`（镜像） |

## 5. GHCR

| 项       | 值                                  |
| -------- | ----------------------------------- |
| 用途     | 镜像仓库（`ghcr.io/baicie/*`）      |
| 写入时机 | 每次 `push: main` 的 image 工作流   |
| 权限     | `packages: write`（工作流内）       |
| 是否自动 | 是                                  |
| 发布对象 | tag（`main`、`sha-`、日期）         |
| 回滚     | 不删镜像；改部署指向旧 digest       |
| 影响     | 仅影响后续拉取；旧 tag 保留即可回滚 |

## 6. TCR（腾讯云容器镜像服务）

| 项       | 值                                  |
| -------- | ----------------------------------- |
| 用途     | 国内镜像加速（`Mirror to TCR` job） |
| 写入时机 | 跟随 image 工作流的镜像推送         |
| 权限     | 工作流 secret                       |
| 是否自动 | 是                                  |
| 发布对象 | tag（与 GHCR 同名）                 |
| 回滚     | 同 GHCR                             |

**注意**：镜像源的实际行为在历史记录里有实测结论（腾讯云加速器不代理 ghcr、VPN 抖动 40 倍、
TCR 内网直连）。回滚时优先用 TCR 内网地址。

## 7. 远程部署脚本

| 项       | 值                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 位置     | `scripts/release/deployment-stage1.ts`、`deployment-stage2.ts`、`deployment-transaction.ts`、`deployment-workspace-restore.ts` |
| 触发     | 由 image 工作流的 deploy job 或人工执行                                                                                        |
| 权限     | SSH（`zeus_playground_deploy`）+ Caddy admin                                                                                   |
| 是否自动 | 随 image 工作流自动                                                                                                            |
| 发布对象 | 容器 + Caddy upstream                                                                                                          |
| 健康检查 | `deployment-acceptance.ts`                                                                                                     |
| 回滚     | `deployment-transaction.ts` 的事务回滚；`deployment-workspace-restore.ts` 恢复工作区                                           |
| 失败恢复 | 事务回滚；Caddy 需原地覆盖（单文件挂载，`sed -i` 会静默失效）                                                                  |
| 影响     | 生产容器替换、流量切换                                                                                                         |

**已知陷阱**（来自历史记录，仍适用）：

- Caddyfile 是单文件挂载，必须原地覆盖；`sed -i` 会静默失效
- `ssh` 空的位置参数会被丢弃，导致后续参数左移，报错像网络故障
- 旧容器可能属于另一个 compose 项目，且与 Caddy 指向不同端口

## 8. 发布操作清单

以下每一步都需要维护者**逐条显式授权**。本文件不构成任何一步的授权。

| #   | 动作                                             | 影响面                                   | 前置条件                          | 可回滚            |
| --- | ------------------------------------------------ | ---------------------------------------- | --------------------------------- | ----------------- |
| 1   | 切版：Core 32 包 → `0.2.0-rc.0`                  | 仓库内版本号                             | 维护者批准版本矩阵                | 是（revert）      |
| 2   | 切版：UI 46 包 → `0.2.0-rc.0`                    | 仓库内版本号                             | 同上；且 1 已合并                 | 是                |
| 3   | 公开 `@zeus-web/dialog` 正式版本，替换 `vendor/` | **RC 阻塞项**                            | 2 已发布                          | 是（恢复 vendor） |
| 4   | 打 Tag `v0.2.0-rc.0`（两仓）                     | git 标签                                 | 1–3 完成                          | 是（删 Tag）      |
| 5   | 发布 npm（Core 32 + UI 46）                      | **不可撤销**（只能 unpublish/deprecate） | 4 完成；`check:rc-readiness` 全绿 | 部分（deprecate） |
| 6   | 修复 dist-tag：`latest` → 稳定版                 | npm dist-tag                             | 5 完成                            | 是                |
| 7   | 部署 Admin Image                                 | **生产**                                 | 5 完成                            | 是（旧 tag）      |
| 8   | 部署 AI Workbench Image                          | **生产**                                 | 5 完成                            | 是                |
| 9   | 发布 Pages                                       | 公开站点                                 | 5 完成                            | 是（revert）      |
| 10  | Stage 2 在线验收（四产品）                       | 只读                                     | 7–9 完成                          | 不适用            |

**第 5 步是唯一不可完全回滚的**。npm 的 `unpublish` 有 72 小时窗口且会破坏已安装者，
`deprecate` 只是标记。因此第 5 步之前的每一道门禁都必须是真的通过。

### 9.1 一个必须记录的缺陷

Admin 与 Playground 的 `build-info.json` 记录 `uiCommit = ffde5592`（2026-11-09，落后 15 个提交），
而冻结 UI SHA 是 `89fc93ca`。根因是 `vars.ZEUS_UI_COMMIT` **不存在**，工作流回退到解析 UI `main`。

Demos Pages 走另一条路径（`git fetch` + 显式 SHA），日志确认用的是 `89fc93ca`——正确。

**产物本身是对的**（线上 dialog chunk 含修复标记），但溯源记录是错的。详见部署事件文档 §3。

## 10. 部署面结论

| 问题                           | 答案                                                                              |
| ------------------------------ | --------------------------------------------------------------------------------- |
| 合并 main 会部署吗             | **会，且无法避免**（除非改工作流）                                                |
| 是否有环境审批门槛             | Admin Image 有 `environment: production`；Demos 有 `demos-pages`；其余无          |
| 发布的是 Tag / Branch / Digest | Pages 是分支；镜像是 tag（另含 `sha-` 不可变 tag）；digest 可用但工作流未直接使用 |
| 回滚是否可行                   | 是，镜像是 tag 回指、Pages 是 git revert、npm 是 deprecate（唯一不可完全回滚）    |
| 对用户的影响                   | Pages 与三个产品的生产环境；npm 影响所有下游安装者                                |
