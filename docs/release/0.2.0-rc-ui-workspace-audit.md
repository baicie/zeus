## 1. 上一份报告的判断不成立

上一份报告写「UI 侧没有等价于 `check:release-artifacts` 的检查，所以 K-4 成立」。维护者指出：**不能因为脚本不存在就判定失败，必须先实测**。

本文件是实测结果。

## 2. 实测方法

1. 用 UI 自己的 `packageRoots` 与 `publishable` 规则枚举出 **46** 个 `@zeus-web/*` 包；
2. 对每个包执行 `pnpm --filter <name> pack`，产出真实 tarball；
3. 解包每一份 tarball，读取其中的 `package.json`；
4. 扫描残留 `workspace:*`、`workspace:^`、`file:`、`link:`；
5. 检查所有 `dependencies` / `peerDependencies` / `optionalDependencies` 里的 `@zeus-web/*` 是否都在本次 46 个 tarball 内；
6. 检查 `exports` 的每个目标文件是否真实存在于 tarball 中。

## 3. 结果

| 检查项                            | 结果                                |
| --------------------------------- | ----------------------------------- |
| 打包成功                          | **46 / 46**                         |
| 残留 `workspace:` 协议            | **0**                               |
| 残留 `file:` / `link:` 依赖       | **0**                               |
| 无法解析的内部 `@zeus-web/*` 依赖 | **0**                               |
| 格式异常的 peer 范围              | **0**                               |
| `exports` 目标检查                | 454 个目标，**4 个不匹配**（见 §4） |

`pnpm pack` 已经正确地把全部 `workspace:` 协议改写成了具体版本号。**上一份报告的 K-4 判断不成立**——UI 侧的 workspace 协议替换是完好的。

## 4. 一个真实缺陷（新的 P1）

`exports` 检查发现 4 处不匹配。其中 3 处是通配符，逐一核实后确认目录真实存在：

| 包                     | 导出                     | 目标                          | 判定            |
| ---------------------- | ------------------------ | ----------------------------- | --------------- |
| `@zeus-web/icons`      | `./svg/*`                | `./dist/svg/*.svg`            | 正常，24 个 svg |
| `@zeus-web/registry`   | `./templates/react/*`    | `./dist/templates/react/*`    | 正常            |
| `@zeus-web/registry`   | `./templates/vue/*`      | `./dist/templates/vue/*`      | 正常，52 个文件 |
| **`@zeus-web/themes`** | **`./components/*.css`** | **`./dist/components/*.css`** | **破损**        |

`@zeus-web/themes` 的 tarball 里 `dist/` 只有 9 个文件：

```
components.css  default.css  neutral.css  slate.css  stone.css
tokens.css  zinc.css  index.js  index.d.ts
```

**没有 `dist/components/` 目录。** 源码里 `packages/themes/src/components/*.css` 有 20+ 个分组件样式文件，但构建只产出了合并后的 `components.css`。

后果：任何消费者写

```ts
import '@zeus-web/themes/components/button.css'
```

都会拿到 `ERR_PACKAGE_PATH_NOT_EXPORTED`。声明的导出承诺了一个不存在的能力。

这与 `@zeus-web/dialog` 的问题同源：**别人怎么用仓库，和仓库怎么用仓库，不是一回事。**

## 5. 判断

| 问题                               | 结论                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------- |
| K-4（UI workspace 协议替换不可靠） | **不成立，撤销**                                                        |
| 是否需要 UI 侧的持续门禁           | **需要**，但理由不是「现在坏了」，而是「现在没人守着」                  |
| 是否发现新的发布缺陷               | **是**：`@zeus-web/themes` 的 `./components/*.css` 导出指向不存在的目录 |
| 该缺陷级别                         | **P1**：不阻断 RC，但会让一个公开导出的入口在使用时失败                 |

## 6. 建议的门禁（本轮不实现）

一个 `check:release-artifacts` 的 UI 等价物，最小实现：

1. `pnpm --filter <each> pack` 到临时目录；
2. 断言 0 个 `workspace:` / `file:` 残留；
3. 断言每个 `exports` 目标在 tarball 内存在（通配符按目录展开后判断非空）；
4. 断言每个内部 `@zeus-web/*` 依赖都在本次打包集合内。

第 3 条会直接抓到 `themes` 的问题，第 2 条会守住 `pnpm pack` 的行为不回退。
