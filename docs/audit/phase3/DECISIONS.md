## D-P3-03（阻塞·高）R-V1 的根治方式

**现状**（VERIFIED）：同时安装 rc.5 与 beta.34 时，磁盘上有 **4 份 `signal`
物理副本**。副本数不等于活跃引擎数——未经 import 的副本不构成风险，所以
"最终应用里有几套活跃引擎"要单独查：模块 realpath、bundler 去重、浏览器行为。

**这项检查已经做了**（2026-11-23，详见 `READINESS.md` 附录）：

| 环境                           | 结果                                                           |
| ------------------------------ | -------------------------------------------------------------- |
| Node 22.12 ESM                 | `A.createSignal === B.createSignal` 为 `false`（2 个活跃引擎） |
| Chrome（Playwright，真实页面） | 同样的错误，`pageerror` 捕获                                   |

跨引擎调用的实际行为是**立即抛错**，不是静默失效：

```
Error: Cannot create an effect with a different Zeus signal engine.
       Deduplicate @zeus-js/signal for this reactive tree.
```

`0.2.0-rc.5` 与 `0.1.1-beta.20` **都带这个检查**，不存在"旧版本没有保护"的窗口。

`--legacy-peer-deps` 能强行安装，却不会修复不匹配的 peer 契约。两个包管理器
行为不同：npm 直接 `ERESOLVE` 拒绝，pnpm 只警告 `✕ unmet peer` 后继续，
到首次跨引擎 effect 才崩。

**可选项**：

| 选项                                                 | 含义                 | 代价 / 风险                                      |
| ---------------------------------------------------- | -------------------- | ------------------------------------------------ |
| A. 发布 beta.35，把 peer 改到 `0.2.0-rc.5`           | 用一次发布消除双版本 | 依赖 D-P3-02                                     |
| B. 用 pnpm `overrides` 强制单一版本                  | 消费者侧强制 dedupe  | 治标；`overrides` 不改变 peer 声明，语义仍不一致 |
| C. 让 `@zeus-web/*` 的 peer 放宽为 `>=0.1.1-beta.20` | 允许跨大版本共存     | 等于宣称 0.1 与 0.2 兼容，事实不是               |
| D. 接受双版本                                        | 不做                 | 运行时立即抛错，组合不可用                       |

**修订建议**：优先发布依赖与 peer 都准确指向 Core rc.5 的兼容 UI 版本，并实测跨宿主运行时唯一性。可保留 Core 与 UI 各自的版本线；独立版本本身不是 R-V1 的根因，真正问题是旧 UI 对 Core beta.20 的依赖锁定。

## D-P3-06（中）Secrets 的最小权限原则

**问题**：本报告 §8 列出了 ecosystem 可能需要的 secrets，但没有区分
"消费已发布 npm 包"与"自己发布 npm 包"。

**修正后的原则**：**只消费 npm 包的仓库不需要 `NPM_TOKEN`。**

| 场景                                      | 需要 `NPM_TOKEN` | 需要 `id-token: write` |
| ----------------------------------------- | ---------------- | ---------------------- |
| ecosystem 只装 `@zeus-js/*`/`@zeus-web/*` | **否**           | 否                     |
| ecosystem 自己发布包                      | 是               | 是                     |
| ecosystem 推送镜像到 TCR                  | 否               | 否（另需 TCR 凭据）    |

Phase 3a/3b（骨架 + 只读消费者）**完全不需要 npm 发布凭据**。
只有未来 ecosystem 自己发包时，才按需授予，且应限定到该 job。

**这是一条需要写进仓库设置的原则**，不是一次性决定。

## D-P3-07（高）需要人工批准的发布与部署动作

以下动作**不可自动执行**，每次都需要明确的人工确认：

| 动作                              | 为什么不可自动                         |
| --------------------------------- | -------------------------------------- |
| 创建 Release Tag（Core 或 UI）    | tag immutability ruleset 下不可回滚    |
| `npm publish`                     | 版本一旦发布不可撤销（只能 deprecate） |
| 切换生产部署                      | 影响线上用户                           |
| 修改 `Release` environment 的规则 | 影响后续所有发布的准入                 |
| 删除或移动已发布的 pairing 记录   | 破坏历史可审计性                       |

**注意**：`Release` environment 当前**没有配置必需审批人**——这是既有决定，
不应在迁移中被"顺手加上"。但它意味着上面这些动作的"批准"依赖人工纪律，
而不是技术强制。这一点应在 Phase 3 的仓库设置中明确写下来。
